# 前端项目需求文档

## 1. 文档范围

本文档仅针对 `ai-m-xxxnavigator` 的前端项目，不包含模型侧、后端接口、训练流程实现和部署平台运维要求。

前端项目目标是构建一套：

- 易于快速部署
- 易于持续修改 UI 展示
- 适合演示智能建模流程
- 具备科技感视觉风格

的前端展示与交互系统。

## 2. 项目背景

该项目面向业务分析师、数据分析师、风控建模人员和低代码建模用户，核心价值是把“数据接入 -> 自动实验 -> 模型交付”三阶段智能建模流程，以清晰、可操作、适合演示的方式呈现在前端。

当前前端已有原型基础，后续工作重点不是扩展复杂框架，而是在不改变核心数据和展示内容的前提下，提升：

- 信息层次
- 阶段进度感知
- 表单输入体验
- 视觉科技感
- 轻量部署和快速迭代能力

## 3. 产品目标

### 3.1 核心目标

1. 将前端项目收敛为轻量演示站，而不是复杂中后台框架。
2. 保证前端可以快速部署到静态站点环境。
3. 保证页面 UI 易于频繁调整，不需要重度工程改造。
4. 保持三阶段建模流程完整清晰，突出流程进度。
5. 保持原型中的数据与显示内容不发生实质变化。

### 3.2 体验目标

1. 第一屏即可让用户理解当前在做什么、进展到哪一步、下一步该做什么。
2. 第一阶段必须突出“建模要求描述”、“自动实验配置”和“上传文件模块”。
3. 自动实验阶段要强化实验轮次、成功/失败状态、最佳结果和部署候选的可见性。
4. 模型交付阶段要明确体现“当前最佳模型已经可以交付”。
5. 整体色调需要体现科技感，但不能牺牲可读性。

## 4. 非目标

本阶段不追求：

- 复杂前端框架设计
- 过度拆分的工程结构
- 真实模型训练逻辑落地
- 完整后端联调
- 多端统一设计系统建设
- 高复杂度权限、工作流、审批系统

## 5. 用户与使用场景

### 5.1 目标用户

- 业务分析师
- 数据分析师
- 风控建模人员
- 黑客松评委与演示观众
- 需要快速理解建模助手流程的产品/技术角色

### 5.2 使用场景

1. 黑客松演示：快速展示端到端建模流程。
2. 产品评审：以静态或半静态数据演示页面能力。
3. 原型迭代：快速微调 UI 和信息展示方式。
4. 后续接真实数据：在不大改 UI 的前提下替换数据来源。

## 6. 核心产品原则

### 6.1 轻量优先

前端必须优先选择容易部署、容易修改、容易交接的方案。允许保留 React/Vite 等轻量工程底座，但不能演变为复杂框架工程。

### 6.2 内容稳定，表现优化

可以优化布局、样式、组件组织和交互反馈，但不能随意改动原型定义的数据内容、实验内容和业务语义。

### 6.3 进度感清晰

三阶段流程必须让用户清楚知道：

- 当前处于哪个阶段
- 当前阶段完成了多少
- 哪些动作已完成
- 下一步是什么

同时阶段进度区域不能占据过大屏幕比例。

### 6.4 表单直接可控

关键实验参数应优先使用直接输入，而不是拖拽控件，方便精确输入、演示和后续 UI 调整。

### 6.5 科技感视觉

整体视觉需要有科技产品感，建议使用：

- 冷色基调
- 蓝青高光
- 深色或半透明卡片层次
- 进度感和数据感强的样式表达

## 7. 功能需求

## 7.1 页面阶段结构

前端工作台应包含三个连续阶段：

1. 数据接入
2. 自动实验
3. 模型交付

每个阶段都要能清晰表达自身目标、阶段状态、关键数据和下一步动作。

## 7.1.1 项目状态驱动的页面模式

前端项目应根据项目状态决定进入不同页面模式，而不是所有项目共用同一套页面。

建议统一三类项目状态：

1. `completed`：已完成项目
2. `running`：进行中项目
3. `created`：创建中项目

对应页面规则如下：

### 已完成项目

适用示例：

- 信用卡逾期预测模型
- 客户流失分析
- 营销响应率预测

要求：

1. 默认进入结果页。
2. 页面显示可选择部署的模型列表。
3. 每个模型展示对应的模型指标数据。
4. 选择某个模型后，页面同步展示该模型详情。
5. 每个模型支持下载对应模型文件压缩包。
6. 即使当前没有真实模型文件，也要创建 mock 文件和 mock 数据，保证交互流程完整。

### 进行中项目

要求：

1. 默认进入过程页。
2. 页面重点展示项目进度、过程 log 和实验 Loops。
3. 页面应显示概览数据，但不显示运行时长。

### 创建中项目

适用示例：

- 新建模项目

要求：

1. 默认进入新建项目页。
2. 页面不显示概览数据。
3. 页面主体聚焦建模输入、自动实验配置和上传文件模块。

## 7.2 阶段导航与进度需求

### 必须满足

1. 页面顶部或主视图区域提供三阶段进度展示。
2. 进度展示需要突出当前阶段状态。
3. 进度区需展示阶段完成度或状态标签。
4. 进度区不能过高，不能压缩主体内容区。

### 展示要求

1. 数据接入阶段显示是否已上传、是否已填写建模要求、配置是否通过。
2. 自动实验阶段显示实验轮次进展、最佳指标、成功实验数量。
3. 模型交付阶段显示当前最佳方案和交付就绪状态。

## 7.3 第一阶段：数据接入与建模输入

### 必须重点突出三个模块

1. 请先描述本次建模要求
2. 自动实验配置
3. 上传文件模块

### 7.3.1 建模要求输入

要求：

1. 该模块应在第一阶段中拥有最高视觉优先级。
2. 应支持自然语言输入建模目标。
3. 应提示建议输入内容，例如预测目标、样本范围、评估指标、交付要求。
4. 可保留推荐提示词或快捷填入能力。

### 7.3.2 自动实验配置

要求：

1. 目标优化指标保留下拉选择。
2. 在指标选择后，必须增加目标值输入框。
3. 目标值输入框用于填写目标指标阈值，例如 `AUC = 0.95`。
4. 目标值输入范围必须限制在 `0 ~ 1`。
5. 超出范围、为空或格式不正确时，必须给出明确提示。

### 7.3.3 实验轮次

要求：

1. 不使用拖拽条。
2. 改为直接输入框。
3. 允许输入实验轮次整数值。
4. 需限制有效范围，并在超出范围时提示规则。
5. 推荐范围为 `1 ~ 8` 轮。

### 7.3.4 验证集比例

要求：

1. 不使用拖拽条。
2. 改为直接输入框。
3. 用户输入 `80` 时展示为 `80%`。
4. 输入值范围改为 `0 ~ 100`。
5. 超出范围时提示：`输入数据超范围`。
6. 超出范围后将数据重置为 `0`。

### 7.3.5 上传文件模块

要求：

1. 支持文件上传与拖拽上传。
2. 文件上传后应展示当前文件名称。
3. 文件解析中应有明确状态反馈。
4. 文件解析完成后，应能清楚表达“可继续提交需求”。
5. 上传区应与自动实验配置和建模要求形成同一阶段的完整闭环。

### 7.3.6 提交需求

要求：

1. 当上传未完成时，不可提交。
2. 当关键配置不满足输入规则时，不可提交。
3. 表单合法后应明确提示“可进入自动实验”。

### 7.3.7 创建中项目页专属要求

当项目处于 `created` 状态时：

1. 不显示概览数据区。
2. 保留三阶段进度区，但处于创建初始态。
3. 页面主体结构以图四为准。
4. 实验轮次使用输入框输入。
5. 验证集比例使用输入框输入。
6. 目标优化指标选择后必须填写目标值输入框。

### 7.3.8 目标值输入规则

要求：

1. 目标值范围为 `0 ~ 1`。
2. 超出范围时提示：`输入数据超范围`。
3. 超出范围后将数据重置为 `0`。
4. 示例：选择 `AUC` 后，输入 `0.95`。

## 7.4 第二阶段：自动实验

### 目标

更突出展示实验进度，而不是只展示静态结果。

### 必须满足

1. 强化实验轮次进度。
2. 强化成功/失败实验状态。
3. 强化当前最佳模型与最佳指标。
4. 保留实验过程视图与结果视图。
5. 支持继续一轮实验。
6. 支持筛选成功实验。

### 进行中项目页面要求

当项目处于 `running` 状态时：

1. 阶段进度展示应参考图一的进行中状态。
2. 过程 log 数据展示应参考图二。
3. 概览数据展示应参考图三。
4. 概览数据中不要展示运行时长。
5. 页面默认进入 `Process` 视图。
6. 页面保留 `Result` 切换入口。
7. 页面保留“只看成功假设”和“下载实验记录”。

### 进行中项目概览数据要求

建议保留：

1. 识别字段
2. 扫描样本
3. 成功 LOOP
4. 最佳 AUC
5. 结果项

明确去掉：

- 运行时长

### 表达要求

1. 应让用户快速看出当前已跑多少轮。
2. 应让用户快速看出哪一轮是当前最佳方案。
3. 应让用户快速理解某轮实验成功还是失败。
4. 结果表格和过程卡片都应保留原有数据内容，不任意删改。

## 7.5 第三阶段：模型交付

### 目标

强化“实验完成后可以交付”的状态感。

### 必须满足

1. 清晰展示当前最佳模型方案。
2. 清晰展示关键指标。
3. 清晰展示交付选项。
4. 强化“模型已准备就绪”的反馈。

### 已完成项目结果页要求

当项目处于 `completed` 状态时：

1. 进入结果页，而不是进入过程页。
2. 页面应显示可选择部署的模型列表。
3. 页面应显示当前选中模型的详细数据。
4. 页面应提供模型文件压缩包下载能力。

### 已完成项目模型选择与下载要求

要求：

1. 每个 completed 项目应提供多个可选模型。
2. 用户切换模型后，模型详情数据同步变化。
3. 每个模型都要支持下载对应模型压缩包。
4. 即使当前没有真实文件，也要创建 mock 压缩包和 mock 数据。
5. 前端需保证“选择模型 -> 查看模型数据 -> 下载压缩包”的完整链路。

### 展示要求

1. 交付内容仍保持原型定义的输出能力。
2. 不必增加复杂流程，但要让交付阶段比原先更直观。

## 8. 技术与实现要求

## 8.1 前端形态要求

前端项目应满足：

- 易部署
- 易维护
- 易改 UI
- 可作为静态站点运行

## 8.2 工程复杂度要求

1. 不采用复杂框架设计。
2. 不引入不必要的抽象层。
3. 尽量把常改部分集中在少量文件中。
4. 状态、样式、展示数据应尽可能清晰集中。

## 8.3 推荐实现原则

1. 可以保留 Vite + React 这种轻量工程底座。
2. 页面数据入口应集中。
3. 交互状态流转应集中。
4. 主题和样式系统应集中。

## 9. 视觉风格需求

### 总体风格

- 科技感
- 冷色调
- 清晰的数据感
- 有层次的卡片界面

### 视觉关键词

- 蓝青色主光
- 深色或半透明面板
- 细线框
- 发光高亮
- 阶段状态明确
- 不走通用中后台灰白风格

## 10. 可部署性需求

1. 前端必须支持快速打包与静态部署。
2. 应适配 Vercel、Netlify、Nginx 等常见静态站点部署环境。
3. 不依赖复杂本地服务才能演示页面。

## 10.1 展示数据组织要求

前端展示数据应升级为按项目组织的数据结构。

要求：

1. 每个项目必须拥有自己的项目状态。
2. 每个项目必须拥有自己的展示数据。
3. completed 项目必须拥有模型列表和下载数据。
4. running 项目必须拥有进度、概览和过程日志数据。
5. created 项目必须拥有表单默认值和输入规则数据。

## 11. 验收标准

满足以下条件时，可认为本阶段前端需求基本达成：

1. 前端项目整体定位明确为轻量演示站，而不是复杂框架应用。
2. 三阶段流程清晰、进度更突出、屏幕占比合理。
3. 第一阶段中“建模要求”、“自动实验配置”、“上传文件模块”成为主视觉重点。
4. 实验轮次改为输入框，校验规则清晰。
5. 验证集比例改为输入框，输入范围为 `0 ~ 100`，超范围时提示并重置为 `0`。
6. 优化指标后具备目标值输入框，输入范围为 `0 ~ 1`，超范围时提示并重置为 `0`。
7. 已完成项目进入结果页，并支持模型选择与压缩包下载。
8. 进行中项目进入过程页，并支持过程展示、概览展示和结果切换。
9. 创建中项目不显示概览数据，只显示项目创建所需输入内容。
10. 自动实验与模型交付阶段的进度感和状态感明显增强。
11. 页面整体视觉具有科技感。
12. 项目便于快速部署和持续修改 UI。

## 12. 后续建议

后续如需继续演进前端，可按以下顺序推进：

1. 继续收敛高频修改入口文件。
2. 将模拟数据结构整理为统一前端契约。
3. 在不改变 UI 主体的前提下接入真实接口。
4. 补充演示模式与真实模式的数据切换机制。
