# 前端项目 Spec 文档

## 1. 文档目的

本文档用于把前端项目需求转化为可执行的实现规范，覆盖：

- 项目定位
- 页面信息架构
- 状态设计
- 交互规则
- 样式主题规范
- 文件组织建议
- 部署与迭代方式

本文档只针对前端项目。

## 2. 项目定位

前端项目定位为：

> 一套面向演示、评审和快速迭代的轻量前端展示系统。

其核心特征是：

- 可静态部署
- UI 可快速迭代
- 工程结构不过度复杂
- 保留三阶段智能建模演示闭环

## 3. 推荐技术基线

## 3.1 基线选型

推荐保留：

- `Vite`
- `React`
- `TypeScript`

原因：

1. 足够轻量
2. 本地开发与打包成本低
3. 静态部署友好
4. 页面状态切换实现简单
5. 后续接真实数据不需要重写页面

## 3.2 不推荐方向

本阶段不建议引入：

- 复杂状态管理框架
- 重型设计系统框架
- 过度拆分的页面层和服务层
- 多主题体系
- 微前端方案

## 4. 文件组织规范

## 4.1 常改核心文件

建议将高频改动收敛到以下文件：

1. `apps/frontend/src/data/mockData.ts`
2. `apps/frontend/src/pages/WorkspacePage.tsx`
3. `apps/frontend/src/styles/global.css`

说明：

- `mockData.ts` 负责展示数据和默认状态
- `WorkspacePage.tsx` 负责主状态流转和阶段切换
- `global.css` 负责整体视觉和主题表达

## 4.2 组件组织原则

组件层允许保留，但应遵守：

1. 只按页面职责拆分，不按抽象层过度拆分。
2. 表单、进度、实验、交付四类组件可以保留。
3. 避免为小型演示需求创建额外状态容器或服务抽象。

## 5. 信息架构

前端工作台由以下区域组成：

1. 侧边栏
2. 顶部项目栏
3. 三阶段进度区
4. 当前阶段摘要区
5. 当前阶段主体区

## 5.1 页面层级

### 一级结构

1. `Sidebar`
2. `Topbar`
3. `StageProgress`
4. `Current Stage Panel`

### 二级结构

根据阶段不同切换：

- `Data Intake Panel`
- `Experiment Workspace`
- `Delivery Panel`

## 5.2 项目状态路由规则

前端应基于项目状态决定进入哪一种页面模式。

推荐状态：

1. `completed`
2. `running`
3. `created`

推荐映射关系：

- `completed` -> Completed Project Result Page
- `running` -> Running Project Workspace Page
- `created` -> Created Project Input Page

要求：

1. 侧边栏项目列表中的每个项目都必须带有自己的状态字段。
2. 点击不同项目后，页面模式由项目状态驱动。
3. 页面模式切换不能只依赖当前阶段字段，还要结合项目状态。

## 6. 三阶段功能 Spec

## 6.1 阶段一：数据接入

### 页面目标

帮助用户完成：

1. 描述本次建模要求
2. 配置自动实验参数
3. 上传数据文件
4. 在满足规则后进入自动实验

### 页面布局要求

建议结构：

1. 阶段摘要卡片
2. 左侧主卡：建模要求
3. 右侧配置卡：自动实验配置
4. 下方上传卡：上传文件模块
5. 底部提交栏

### 关键优先级

视觉优先级从高到低：

1. 建模要求输入
2. 自动实验配置
3. 上传文件模块
4. 状态提示与提交按钮

### 字段规则

#### 建模要求

- 类型：多行文本
- 必填：否
- 作用：增强实验语义理解

#### 目标优化指标

- 类型：下拉选择
- 选项：`AUC`、`KS`、`F1 Score`、`Accuracy`、`Recall`

#### 目标值

- 类型：数值输入
- 位置：紧跟在目标优化指标后
- 范围：`0 ~ 1`
- 示例：`0.95`
- 错误提示：超出范围时提示 `输入数据超范围`
- 超范围处理：重置为 `0`

#### 实验轮次

- 类型：数值输入
- 范围：`1 ~ 8`
- 约束：整数
- 说明：不使用滑块

#### 验证集比例

- 类型：数值输入
- 范围：`0 ~ 100`
- 展示：输入 `80` 时界面显示 `80%`
- 说明：不使用滑块
- 错误提示：超出范围时提示 `输入数据超范围`
- 超范围处理：重置为 `0`

### 提交规则

提交按钮可用条件：

1. 已上传文件
2. 文件未处于解析中
3. 实验配置合法

提交按钮不可用条件：

1. 未上传文件
2. 文件仍在解析
3. 实验轮次非法
4. 验证集比例非法
5. 目标值非法

## 6.1.1 Created Project Page Spec

当项目状态为 `created` 时，进入新建项目页。

页面要求：

1. 不显示概览数据区。
2. 保留三阶段进度区，但状态处于创建初始态。
3. 页面主体聚焦输入和配置。
4. 页面布局参考图四。

页面主体应包含：

1. 建模目标 / 提示词输入区
2. 自动实验配置区
3. 上传文件模块
4. 提交需求区

## 6.2 阶段二：自动实验

### 页面目标

用更强的进度表达展示多轮实验过程和结果，而不是简单列表化展示。

### 页面结构

1. 阶段摘要 / 最佳方案区
2. 实验总进度区
3. 实验视图切换区
4. Loop 列表区
5. 过程视图区 或 结果视图区
6. 底部追加实验操作区

### 必要交互

1. 切换过程视图 / 结果视图
2. 只看成功假设
3. 选择某个 Loop
4. 展开某个实验项详情
5. 下载实验记录
6. 继续一轮实验
7. 跳转模型交付

## 6.2.1 Running Project Page Spec

当项目状态为 `running` 时，进入进行中项目页。

页面组成：

1. 阶段进度区
2. 概览数据区
3. 过程 / 结果切换区
4. 实验 Loops 列表区
5. 当前 Loop 详情区

要求：

1. 阶段进度区参考图一的进行中状态。
2. 概览数据区参考图三，但移除运行时长。
3. 过程 log 数据展示参考图二。
4. 默认进入 `Process`。
5. 支持切换到 `Result`。
6. 支持只看成功假设。
7. 支持下载实验记录。

### 状态表达要求

每个 Loop 必须具备：

- Loop 名称
- 成功/失败状态
- 指标值
- 是否当前选中

实验摘要区必须具备：

- 当前最佳 Loop
- 最佳指标
- 已完成轮次 / 目标轮次
- 当前是否达到目标阈值

## 6.3 阶段三：模型交付

### 页面目标

突出“最佳方案已产生并可交付”的状态，帮助完成最终演示闭环。

### 页面结构

1. 交付摘要区
2. 关键指标区
3. 交付选项区
4. 交付说明区
5. Ready 状态区

### 必要内容

1. 当前最佳模型名称
2. 最佳指标值
3. 目标阈值
4. 最佳 KS
5. 验证集比例
6. 交付选项列表
7. 交付就绪说明

## 6.3.1 Completed Project Result Page Spec

当项目状态为 `completed` 时，进入结果页。

页面组成建议：

1. 项目结果摘要区
2. 可部署模型列表区
3. 当前选中模型详情区
4. 模型下载区

模型列表数据建议：

1. `modelId`
2. `modelName`
3. `version`
4. `primaryMetric`
5. `ks`
6. `status`
7. `downloadUrl`
8. `packageName`
9. `summary`

交互要求：

1. 点击模型列表项后更新当前模型详情。
2. 下载按钮必须绑定对应模型压缩包。
3. 即使当前没有真实文件，也应提供 mock zip 包，保证完整演示。

## 7. 状态设计 Spec

## 7.1 前端核心状态

推荐保留以下主状态：

- `currentStep`
- `uploadedFile`
- `modelingRequirement`
- `requirementSubmitted`
- `experimentRounds`
- `experimentRoundsInput`
- `optimizationMetric`
- `optimizationTarget`
- `optimizationTargetInput`
- `validationRatio`
- `validationRatioInput`
- `experimentView`
- `successfulOnly`
- `activeLoopId`
- `expandedExperimentId`
- `experimentLoops`
- `isProcessing`
- `selectedChat`

## 7.2 校验状态

建议在页面状态流中派生以下校验结果：

- `experimentRounds` 错误
- `validationRatio` 错误
- `optimizationTarget` 错误
- `configValid`

说明：

这些状态可以不单独存储，但必须可被组件稳定读取和渲染。

## 8. 视觉主题 Spec

## 8.1 视觉方向

推荐视觉主题：

- 深色背景
- 蓝青发光主色
- 轻玻璃拟态面板
- 低饱和辅助文字
- 清晰的进度高亮

## 8.2 色彩规范

建议角色如下：

- 背景主色：深蓝黑
- 主品牌色：高亮蓝青
- 辅助品牌色：冷蓝
- 成功色：清亮青绿
- 失败色：偏亮红粉
- 分割线：低透明冷色细线

## 8.3 样式表达原则

1. 进度和状态比装饰更重要。
2. 卡片层级要明显，但不堆砌阴影。
3. 文字必须始终保持良好可读性。
4. 科技感来自色彩、层次和信息结构，不来自无意义特效。

## 9. 响应式 Spec

## 9.1 桌面端

1. 三阶段导航可横向展示。
2. 第一阶段可采用左右分栏。
3. 自动实验区可采用轨道栏 + 主面板结构。

## 9.2 中小屏

1. 阶段区改为纵向堆叠。
2. 第一阶段模块改为单列。
3. 结果表格允许降级为卡片纵排。
4. 提交按钮、切换按钮应支持整行展示。

## 10. 数据与内容约束

## 10.1 数据约束

前端在优化过程中必须遵守：

1. 不随意改变原型中的实验数据内容。
2. 不随意改变原型中的业务文案语义。
3. 可以优化呈现方式，但不能改动数据含义。

## 10.2 内容约束

允许变化：

- 布局
- 样式
- 组件组织
- 状态提示方式
- 阶段摘要表达

不允许随意变化：

- 实验结果含义
- Loop 内容
- 交付项语义
- 核心三阶段定义

## 10.3 项目级展示数据结构规范

展示数据建议从“全局散数据”升级为“项目级数据结构”。

每个项目至少应包含：

1. `projectId`
2. `projectName`
3. `status`
4. `entryView`
5. `summary`
6. `dataset`

按状态补充：

### created 项目

1. `formDefaults`
2. `validationRules`
3. `uploadHints`
4. `requirementTemplates`

### running 项目

1. `overviewMetrics`
2. `loops`
3. `activeLoopId`
4. `processLogs`
5. `resultRows`

### completed 项目

1. `models`
2. `defaultSelectedModelId`
3. `downloadablePackages`
4. `deploymentSummary`

## 11. 部署 Spec

## 11.1 构建目标

前端产出应支持：

- 静态构建输出
- 标准 `dist/` 目录部署

## 11.2 部署平台

兼容目标：

- Vercel
- Netlify
- Nginx 静态资源服务器
- 其他静态托管平台

## 11.3 运行约束

前端页面不应依赖复杂本地服务才能展示基础流程。

## 12. 修改成本控制 Spec

为了保证“易改 UI 展示”，建议遵守以下约束：

1. 页面主流程集中在一个页面入口文件。
2. 主题变量集中在一个全局样式文件。
3. 模拟数据集中在一个数据文件。
4. 不为简单需求引入额外抽象层。
5. 避免一个样式规则同时散落在多个文件中。

同时建议：

1. 展示数据统一放在可单独维护的数据文件中。
2. 页面组件只读取统一数据入口，不直接内嵌展示内容。

## 13. 交付物

本阶段前端项目应至少交付：

1. 一套可访问的前端页面
2. 一份清晰的需求文档
3. 一份可执行的前端 spec 文档
4. 可静态部署的构建产物

## 14. 实施优先级

### P0

1. 轻量可部署项目形态
2. 第一阶段输入改造
3. 三阶段进度优化
4. 科技感主题建立

### P1

1. 自动实验阶段进度强化
2. 模型交付阶段状态强化
3. 统一移动端适配

### P2

1. 接真实数据适配层
2. 下载/导出真实能力
3. 演示模式和真实模式切换

## 15. 验收清单

前端实现应满足以下核对项：

- 是否仍保持轻量项目形态
- 是否支持静态部署
- 是否易于集中修改 UI
- 是否强化了三阶段进度感
- 是否突出第一阶段三个核心模块
- 是否取消实验轮次与验证集比例滑块
- 是否增加优化指标目标值输入
- 是否具备明确输入规则提示
- 是否支持项目状态驱动的页面模式
- 是否支持 completed 项目的模型选择与压缩包下载
- 是否支持 running 项目的过程页和概览页
- 是否支持 created 项目的创建页独立模式
- 是否整体视觉更具科技感
- 是否不改变原始业务数据与结果语义
